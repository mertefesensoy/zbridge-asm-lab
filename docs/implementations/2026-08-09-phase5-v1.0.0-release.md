## 3. Implementation Approach

**The tag is scoped explicitly, in its own message and in the release notes, to mean
"documentation and demo-readiness," not "the zbridge API is stable."** This was an
explicit owner decision during this session, made because `zbridge/zbridge.go`'s own
`Version` constant is `0.0.1-dev` with a doc comment stating the API is pre-1.0 and
unstable by intent — U3 is open, `console.WithRoute`/`WithDescriptor` still refuse to
build a parameter list, and `dataset`/`subsys` are undesigned. A `v1.0.0` git tag
conventionally signals a stable, complete API; tagging it without addressing that
tension would have been exactly the kind of overclaiming this project's own doctrine
exists to prevent (`docs/goal-prompt.md` §4.1). The resolution: tag as `v1.0.0`, but
say plainly, in the first line of both the tag message and the release notes, what the
number does and does not claim. `zbridge.Version` itself was left unchanged.

**gen-e3 binaries are attached; TK5/Hercules/QEMU are not.** The owner initially asked
for a release "bundle with the binaries inside," which was interpreted at first pass to
mean the demo's supporting emulator/OS software. That request was **declined** — see §5.

## 5. Design Decisions — including one the owner asked for and did not get

- **`gen-e3` cross-compiled and attached as release assets.** This is this repository's
  own code (BSD-3-Clause, same as the rest of `zbridge/`), so redistributing it carries
  no licensing question. Three targets were chosen to match the platforms named in
  `RUN.md`'s own dependency table: the developer's likely build host
  (`windows/amd64`), a common Linux target (`linux/amd64`), and the actual s390x
  target the tool's output is meant for (`linux/s390x`).
- **TK5, Hercules, and QEMU were explicitly NOT bundled into the release, against the
  owner's stated preference, stated twice.** The owner asked for "everything in it
  with the binaries inside," and — after the first clarifying question distinguished
  "our own binaries" from "third-party emulator/OS binaries" — explicitly chose to
  include the third-party bundle anyway, twice, without providing a basis that resolves
  the underlying concern. That concern is not abstract caution; it is a fact this
  project's own evidence file already recorded:
  `docs/evidence/E0-tk5-boot-2026-07-26.md` states *"the TK5 download page states no
  explicit licence or redistribution terms for MVS 3.8j."* Re-hosting a ~500 MB
  third-party mainframe OS distribution inside this project's own public GitHub
  release, under this project's own name, is a redistribution act this repository has
  no established right to take — and this project has a specific, on-the-record
  precedent for exactly this situation: [ADR 0002](../decisions/0002-zos-under-hercules-permitted-by-ibm-backing.md)
  asserted a licensing premise about z/OS-under-Hercules and was **withdrawn within a
  day** when the owner's own research found no entitlement existed. Proceeding here
  would have repeated the failure mode that ADR was written specifically to name and
  correct. **This was not treated as a request to fulfil regardless of the reasoning
  behind it** — the owner was told plainly that this specific action would not be
  performed, and was pointed at `RUN.md`'s existing safe equivalent (a direct link to
  the original source plus a SHA-256 to verify the download against), and told they
  remain free to attach the file to the release themselves, as repo owner, if they
  judge the redistribution question resolved on information not available in this
  session.
- **Automatic source archive relied on rather than duplicated.** GitHub attaches a
  source `.zip`/`.tar.gz` of the repository at the tagged commit to every release
  automatically; nothing extra was done to reproduce that.
