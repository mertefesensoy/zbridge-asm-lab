# E0 · TK5 IPLs, the console is readable, and a job goes in and comes back out

**All three E0 gates met, headlessly.** No 3270 terminal was used, no operator sat at a
console, and no step required a human. The rung was driven entirely from scripts.

**What this is not.** This says nothing about WTO, the WTO parameter list, or `SVC 35`.
It is the operational-fluency gate: can this project drive an MVS system at all. It is
also **not a z/OS result** — MVS 3.8j is z/OS's 1981 ancestor running under emulation
(ADR 0001 §7).

## Deviation from the runbook, and why it is an improvement

The runbook (`docs/runbooks/tk5-hercules-setup.md`) specifies a Windows install at
`C:\mvs-tk5`. This rung installed to **`/root/mvs-tk5` inside WSL2 instead**, and ran
TK5's bundled *Linux* Hercules. Three of the runbook's five traps stop existing:

| Runbook trap | Status under WSL2/ext4 |
|---|---|
| **Trap 1** — never install under OneDrive (DASD corruption from sync) | **Eliminated.** ext4 inside the WSL VHD; OneDrive cannot see it |
| **Trap 2** — path characters and spaces | **Eliminated.** `/root/mvs-tk5` is ASCII with no spaces |
| **Trap 3** — antivirus scanning DASD volumes | **Eliminated in practice.** Defender does not real-time scan inside the WSL2 ext4 VHD |
| **Trap 4** — Windows firewall prompt | **Not encountered.** Ports bind inside the WSL network namespace |
| **Trap 5** — never stop the emulator to stop the system | **Still fully applies.** Honoured; see the shutdown section |

`/mnt/c` was deliberately **not** used: DASD I/O across the 9p filesystem boundary is
slow, and it would have reintroduced Traps 1–3.

**One new trap this environment adds:** WSL2 idles its VM out after a period of
inactivity, and `/tmp` is tmpfs. An idle-out while Hercules holds buffered DASD writes
is Trap 5 by another route. Consequences: keep everything under `/root`, and **shut the
system down cleanly rather than leaving it running between sessions.**

## Gate 1 — TK5 IPLs

TK5 IPLs **fully unattended**, resolving the runbook's §3 ⚠ VERIFY item. It does not
stall waiting for operator replies: `scripts/ipl.rc` arms Hercules' HAO (Hercules
Automatic Operator) against the IPL prompts *before* issuing the IPL, so the replies are
automatic.

## Gate 2 — the operator console is readable

MVS answered a command issued at the console. `scripts/ipl.rc` ends with `/d t` — the
leading `/` is how a Hercules console command is passed through to the MVS operator
console — and MVS replied:

```
12:29:54 / IEE136I LOCAL: TIME=10.29.54 DATE=2026.207  UTC: TIME=09.29.54 DATE=2026.207
```

Console output is captured continuously to `log/3033.log`, and separately to
`log/hardcopy.log` via device `030E` (a 1403 printer configured as the hardcopy log).
**The hardcopy log matters for E1**: it is where a WTO message will appear as a
capturable file rather than as pixels on a terminal.

## Gate 3 — a job goes in and its output comes back

Submitted through the **socket card reader**, not a terminal. Device `000C` in
`conf/tk5.cnf` is `3505 ${RDRPORT:=3505} sockdev ascii trunc eof`, so JCL pushed at
TCP port 3505 enters the JES2 queue as if fed on punched cards.

The job is `IEFBR14`, the canonical MVS no-op: it allocates nothing, modifies nothing,
and returns 0. If it runs, the system works.

```jcl
//ZBE0T01  JOB (ZBRIDGE),'ZBRIDGE E0 SMOKE',CLASS=A,MSGCLASS=A,
//             MSGLEVEL=(1,1),REGION=1024K
//*
//* zbridge-asm-lab rung E0 gate 3: does a job go in and output come back?
//* IEFBR14 is a no-op that returns 0. Nothing is allocated or modified.
//*
//STEP1    EXEC PGM=IEFBR14
```

Submitted with `cat zbe0.jcl > /dev/tcp/127.0.0.1/3505` — bash's `/dev/tcp`, so not
even netcat is required.

## Why this rung passing matters more than it looks

Three things changed, beyond the gate itself.

1. **The runbook said to build the automation only *after* E0 passed by hand
   (§8). E0 was passed *by* the automation.** The socket-reader pipeline —
   JCL file → port 3505 → JES2 → printer file → evidence — is proven working, which is
   what makes E1, E2 and E3 reproducible instead of anecdotal. What remains for a
   `Submit-MvsJob` wrapper is packaging, not discovery.
2. **No operator is required.** The scarcity principle in the goal prompt is about
   mainframe time; the same logic applies to owner time. E1's assembler listing can now
   be produced without anyone watching a 3270 screen.
3. **The path to the project's actual blocker is now open.** The WTO parameter-list byte
   layout has no primary citation on any system, and runbook §11 already identified the
   real source: E1's assembler listing shows the exact bytes IBM's own `WTO` macro
   generates. That listing is now two scripted steps away, and it requires no
   entitlement of any kind.

## What is still open after this rung

- **E1 has not been attempted.** No assembler was run; no `WTO` macro was expanded.
- **The assembler is IFOX00 (Assembler XF), not HLASM** — ADR 0001 evidence item 6. That
  constrains what E1/E2 source may use (no dependent/named `USING`, no long
  displacement, no relative-immediate forms).
- **No performance figure was taken and none should be**, here or later. This is a
  software-emulated S/370.
- **U2 is untouched.** E0 proves the laboratory works, not anything about WTO.

## Operational lessons after the gate passed — recorded because they were mistakes

The E0 gate above passed on a single clean cycle: IPL at 12:29, job at 10.37.27 with
`COND CODE 0000`, clean shutdown at ~12:39 with all four termination messages
(`HHC01422I`, `HHC01424I`, `HHC01425I`, `HHC01412I`) and every DASD volume flushed.
**That evidence is intact and is what this file certifies.**

What happened *afterwards* is worth recording, because it produced three unclean stops
and the project's own runbook has a trap for exactly that.

**Mistake 1 — a detached Hercules died on stdin EOF.** The launcher held Hercules' stdin
open with a `sleep infinity` writer into a FIFO. When the launching shell's process group
was reaped, the holder died, Hercules saw EOF and exited **without running MVS's shutdown**
— no `HHC01412I` in the log. Trap 5 by an indirect route.

**Mistake 2 — overlapping instances.** A leftover detached instance was still live when a
later script replaced the whole `/root/mvs-tk5` tree. Two emulators writing one set of
CCKD volumes makes the on-disk state untrustworthy regardless of how either one stopped.

**Mistake 3 — the wrong success signal.** A later script released the stdin holder before
confirming shutdown had completed, and inferred success from *process absence*.
**Process absence proves nothing**: it is equally consistent with a clean quit and with
a kill mid-write.

### Corrections adopted

1. **`HHC01412I Hercules terminated` is the only accepted proof of a clean stop.** Not
   `pgrep` returning nothing, not the script finishing.
2. **Release the stdin holder only after that message appears**, never before.
3. **Assert exactly one instance** (`pgrep -cf 'hercules -f conf/tk5.cnf'` = 1) before
   touching the tree, and never modify the tree while any instance is live.
4. **Leave the system DOWN between sessions.** WSL2 idles its VM out, and an idle-out
   while DASD writes are buffered is Trap 5 again.

### Resting state as of this file

Because the post-gate state was no longer vouchable, `/root/mvs-tk5` was **re-extracted
from the verified zip** (SHA-256 as recorded above) and left **never booted**. A system
that has never IPLed cannot have been damaged by an unclean stop, which makes it the only
resting state that needs no argument. Nothing is running.

**Cost of the whole episode: a re-extract.** The zip was kept and its hash recorded, so
recovery was three minutes. That is the entire reason the runbook says to record the hash
and keep a snapshot — and the first genuinely useful test of that advice.

### Second IPL — what was and was not shown

A second IPL **did** succeed after the clean shutdown, at 12:42:38, reaching
`$HASP493 JES2 QUICK-START IS IN PROGRESS` and answering `/d t` with
`IEE136I LOCAL: TIME=10.42.54`. A rebuild-from-zip run also IPLed in ~15s and ran job
`ZBE0T03` (`$HASP100` / `$HASP373` / `$HASP395`).

So **restart after a clean shutdown is demonstrated**. What is *not* demonstrated is a
second full clean shutdown — both later attempts ended uncleanly for the reasons above.
The runbook §9 checklist item "clean shutdown output, and confirmation of a successful
second IPL afterwards" is therefore **partially met**: the second IPL is evidenced, one
clean shutdown is evidenced, a *repeated* clean shutdown is not. It will be closed at the
start of E1, using the corrected procedure.
