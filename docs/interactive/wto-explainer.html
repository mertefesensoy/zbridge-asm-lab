WTO from Go assembly

What the project proved, in the order you would explain it to someone who knows MVS better than you do. Every hex value on this page came off a real system — none of it is illustrative.

1 · The one-sentence version

We are building WTO(message string) error — a Go function that writes to the z/OS operator console — implemented in pure Go assembly, with no cgo. ibmruntimes/go-recordio proved a Go program can call an MVS service directly, but it only covers IEFSSREQ. Operator-facing services like WTO have no public Go-assembly implementation. That gap is the thesis.

Today the parameter list this function has to build was verified byte-for-byte against IBM's own macro, and bytes produced by our Go code were accepted by a real SVC 35.

2 · Three unknowns — the spine of every decision

If you only remember one framework, remember this one. It is what turns "we don't have a mainframe" from a blocker into a work plan.

3 · The ladder, and what each rung actually proved

  1. E0
    The laboratory works

    TK5 IPLs unattended, the console is readable, a job goes in and output comes back. Driven entirely through the socket card reader on port 3505 — no 3270 terminal, no operator. IEFBR14, COND CODE 0000.

  2. E1
    The layout, from IBM's own macro

    Assembled WTO 'text',MF=L under IFOX00 with PRINT ON,GEN,DATA and read the expansion. This is the primary source — there is no prose manual that documents it.

  3. E2
    We understand it, not just how to call a macro

    Parameter list hand-built as DC constants, LA 1,WPL, raw SVC 35. No WTO macro anywhere in the program. Reached the console. This is the rung that retires U2.

  4. E3
    Go's bytes crossed

    Go cannot run on MVS 3.8j — but its bytes can. console.EncodeWPL built the list on a Windows laptop, FormatDC rendered it into DC X'…', and a real SVC 35 accepted it.

  5. T3
    WTO on a z/OS console

    Still ahead. Needs entitled z/OS access and IBM's Go fork.

Where this comes from

LOC OBJECT CODE STMT SOURCE STATEMENT 000000 7 WPLMIN WTO 'ZBRIDGE TEST HELLO',MF=L 000000 8+WPLMIN DC 0F'0' 000000 0016 9+ DC AL2(22) TEXT LENGTH 000002 0000 10+ DC B'0000000000000000' MCS FLAGS 000004 E9C2D9C9C4C7C540 11+ DC C'ZBRIDGE TEST HELLO' MESSAGE TEXT 00000C E3C5E2E340C8C5D3 000014 D3D6

The length field is len(text) + 4 — and now you can say why instead of just quoting the rule: it counts its own two bytes, plus the two flag bytes, plus the text. It is a length of header plus text, not a length of text. Confirmed at two lengths: 18 characters gave 0x0016 (22), 38 gave 0x002A (42).

The trap. Switch to the routed form above and watch the length field. Four more bytes are appended after the text — descriptor codes and routing codes — and the length field still reads 22. So "length = the whole parameter list" is wrong. It only ever covers the four header bytes plus the text. An implementation that got this wrong would look correct until someone passed a routing code.

The routed form also tells us what MCS flag bit 0 (0x8000) means: the descriptor and routing halfwords are present. Our research brief could not find a citable bit table for the other fifteen bits, which is exactly why our library refuses routing options rather than guessing at them.

5 · The dangerous part: two ABIs want the same registers

This is the detail most likely to break the real implementation, and the one worth raising with your mentor unprompted.

RegStandard MVS linkageGo on s390xCollision
R1parameter list addressgeneral use—
R13address of a 72-byte save area the goroutine pointer g (REGG) YES
R14return addresslink register agrees
R15entry point in, return code out the stack pointer (REGSP) YES

Clobber R13 and the Go runtime cannot find the current goroutine. Clobber R15 and there is no stack. A Go assembly routine that establishes MVS linkage has to save both, set the MVS values, call the service, and restore both before returning to Go. These assignments are not folklore — they are in cmd/internal/obj/s390x/a.out.go: REGG = REG_R13, REGSP = REG_R15.

6 · Why s390x is the right machine for this

The exercises deliberately write naive assembly on amd64, then let the target architecture collapse it. Here is the payoff, with real encodings.

EBCDIC translation

On amd64, seven instructions per byte: load, index the table, store, two pointer bumps, decrement, branch. On s390x it becomes two block instructions per 256 bytes:

16ae8e: d2 ff 20 00 40 00 mvc 0(256,%r2),0(%r4) copy the block 16ae94: dc ff 20 00 30 00 tr 0(256,%r2),0(%r3) translate it in place

Two honest corrections worth making yourself before anyone makes them for you. First, TR translates in place, so a two-buffer API costs MVC then TR — the roadmap's "one instruction replaces the loop" is not literally true. Second, Go's s390x assembler has no TR mnemonic at all — 729 mnemonics and the translate family is absent — so those six bytes are hand-encoded, then verified by disassembling them with GNU objdump, which does know the instruction.

Why that matters far beyond ebcdic. There is no SVC mnemonic either. So SVC 35 — the whole endgame — will have to be hand-encoded the same way: BYTE $0x0A; BYTE $0x23. Today's exercise was an unintentional rehearsal of the exact technique the thesis needs. The precedent is inside the Go distribution: x/sys/unix/asm_zos_s390x.s encodes SVC 08 exactly like this.

The other two collapses

Exerciseamd64s390xWhat it buys
strmanip SHRQ + two MOVB to build a big-endian halfword by hand MOVH — one instruction The WPL starts with a big-endian halfword. On z/Architecture the natural store already puts the high byte first.
bytecmp per-byte load, compare, branch CLC — compares up to 256 bytes and sets the condition code The comparison is the instruction: no index register, no loop counter.

7 · The divergence you must not gloss over

MVS 3.8j and z/OS disagree about return codes, and it is documented on both sides.

MVS 3.8jz/OS
Return code for a single-line WTO None issued at allYes, in R15
R1 on return 24-bit message identification number message identification number

Consequence: rung E3 cannot prove the "read R15, map to a Go error" step, because the ancestor system has nothing to read. Our error type therefore carries a HasCode bool alongside the code, so "the service returned nothing" is a representable state rather than indistinguishable from "returned zero". That field was added from reading GC28-0683-2 p.210 directly, before the research return independently confirmed the divergence.

8 · What is still genuinely open

  • All of U3. Malloc31, AMODE switching, and the GOOS=zos toolchain. No emulator reaches any of it.
  • Upstream Go cannot target z/OS. go tool dist list offers linux/s390x and no zos/s390x. IBM's fork is a hard dependency — and that is a separate question from a z/OS licence.
  • The MCS flag bit table. One bit is attested; the rest are not.
  • Everything z/OS-side. The layout is verified on the 1981 ancestor. That is what makes it evidence rather than proof.

Before the meeting — say these out loud

If you can answer without looking, you can hold the conversation.

  1. Why is the length field text + 4?
    Because it counts its own two bytes and the two MCS flag bytes as well as the text. It is a length of header-plus-text. And in the routed form it still excludes the trailing descriptor and routing halfwords.
  2. Why did you assemble a macro instead of citing a manual?
    Because no IBM publication documents the byte layout in prose, and none prints the generated expansion. PRINT GEN is the authoritative instrument, so the assembler listing is the primary source. We found this out after reading GC28-0683-2 page by page and discovering it does not contain the layout at all.
  3. What does rung E3 prove that E1 does not?
    E1 proves IBM's macro works. E2 proves we understand the layout, because we built it by hand and issued a raw SVC 35. E3 proves our Go code's bytes are accepted — without Go ever running on a mainframe.
  4. Which two registers make this dangerous, and why?
    R13 and R15. MVS linkage wants R13 for the save area and R15 for the entry point and return code; Go reserves R13 for the goroutine pointer g and R15 for the stack pointer. Clobber either and the Go runtime breaks.
  5. Why can't rung E3 retire the "read R15" step?
    Because MVS 3.8j issues no return code for a single-line WTO — R1 comes back with the message ID instead. z/OS does return one. It is a documented divergence, not a gap in our testing.
  6. What is the biggest remaining risk?
    The toolchain. Upstream Go has no zos/s390x target, so IBM's Go fork is a hard dependency — and obtaining it is a different question from obtaining a z/OS system to run on.
