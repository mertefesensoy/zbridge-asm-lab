The cgo fallback

Every term you need, then the one question. Read section 5 first if you want the punchline — it changed my own view of this decision.

1 · What is actually being decided

Your roadmap asks Jürgen a hedging question: should the target be downscaled — do WTO the easy way first (through cgo), and treat the direct SVC 35 version as a stretch goal?

That question was written before we had any evidence. We now have quite a lot. The decision is whether to close it ourselves and commit to the direct route, or leave it open for him to rule on.

2 · The terms

Each one includes why it matters to this decision, not just what it means.

cgo
Go's mechanism for calling C functions from Go code.
Why it matters: using it means a C compiler is required at build time, and the resulting binary is no longer a self-contained pure-Go executable. Go's headline property — one static binary, no runtime dependencies — is what you give up.
Language Environment (LE)
IBM's shared runtime on z/OS that C, COBOL and PL/I programs all execute under. It provides storage management, condition handling, and the C library.
Why it matters: on z/OS, "using C" means "running under LE." A cgo build inherits LE as a dependency. Your thesis statement is explicitly "no cgo, no Language Environment dependency" — these are the same commitment stated twice.
__console2()
A function in the z/OS C library that writes a message to the operator console.
Why it matters: it is the "easy path." Underneath, it does what you are doing by hand — builds a parameter list and issues the supervisor call. The difference is not what reaches the console; it is who builds the parameter list. Calling it from Go means Go → cgo → LE → C library → WTO.
WTO · SVC 35
Write To Operator. On MVS and z/OS, a service is invoked by a supervisor call — the instruction SVC n traps into the operating system, and n selects the service. WTO is service 35.
Why it matters: this is the direct route. You build the parameter list yourself, put its address in register 1, and issue SVC 35. No C anywhere.
Problem state · key 8 · APF authorization
z/OS separates privileged code (supervisor state, authorized) from ordinary application code (problem state, storage key 8). APF is the mechanism that grants a program authorization.
Why it matters: WTO works from problem state without authorization. That is why it is a viable student-project target — you do not need special privileges on someone else's system. Unauthorized messages get a prefix character on the console (we observed +), which is cosmetic, not a block.
Parameter list · WPL
The block of bytes a service reads its arguments from. For WTO it is the WTO Parameter List: a 2-byte length, 2 bytes of MCS flags, then the message text in EBCDIC.
Why it matters: this is the thing we spent two days proving. Getting it byte-correct is the whole difficulty of the direct route, and it is now verified against IBM's own macro and accepted by a real SVC 35.
EBCDIC · IBM-1047 · AtoE
Mainframes encode text in EBCDIC, not ASCII or UTF-8. IBM-1047 is the code page z/OS UNIX uses. AtoE converts one to the other through a 256-byte table.
Why it matters: the message text inside the parameter list must be EBCDIC. This is done and verified on both architectures.
Malloc31 · "below the bar" · AMODE 31 / AMODE 64
z/OS programs can address memory in 31-bit mode (up to 2 GB — "below the bar") or 64-bit mode. Many MVS services are old and only accept 31-bit addresses. Malloc31 allocates storage a legacy service can reach; AMODE switching moves between the two modes around the call.
Why it matters: this is the one piece still genuinely unknown. It cannot be tested on any emulator, and it is the one place the project accepts an LE touchpoint — go-recordio exposes a helper for it.
GOOS=zos · IBM's Go fork
Go's build system targets an operating system and architecture pair. Upstream Go supports linux/s390x but not zos/s390x — I verified this against the toolchain source.
Why it matters: you cannot compile a Go program for z/OS with stock Go at all. IBM maintains a fork that can. This is a hard dependency of the endgame, and — importantly for this decision — both routes need it equally.
ibmruntimes/go-recordio
An IBM-published Go module that calls the MVS subsystem-request service (IEFSSREQ) directly from Go assembly, with no cgo.
Why it matters: it is the existence proof that the direct route works at all. Your project applies the same pattern to a service nobody has published a Go implementation for.
Fallback vs. baseline
A fallback is what you ship if the main plan fails. A baseline is something you keep only to measure against.
Why it matters: this is the actual fork in the question. Option 3 keeps cgo as a baseline while dropping it as a fallback.

3 · The two paths, side by side

Direct — what you are building

Go program Go assembly builds the WPL load R1 with its address SVC 35 operator console
  • No C compiler
  • No Language Environment
  • Static Go binary preserved
  • Needs: IBM's Go fork
  • Hard part: getting the parameter list byte-correct — done

cgo — the proposed fallback

Go program cgo boundary C code under LE __console2() …builds a WPL and issues SVC 35 operator console
  • Needs a C compiler on z/OS
  • Drags in Language Environment
  • Static binary lost
  • Needs: IBM's Go fork as well
  • Hard part: none — IBM already wrote it

Both paths end at the same instruction. The difference is whether you build the parameter list or IBM's C library does — and the whole thesis is that doing it yourself, from Go, with no C, has never been published for this service.

4 · What the evidence changed

Below-the-bar storage and AMODE switching Still open — needs z/OS

Everything the cgo hedge was designed to protect against has been answered. What remains open is access, not feasibility.

5 · The thing that decides it

The fallback needs strictly more than the plan it insures

A fallback is only insurance if it survives the failure it is meant to cover. Line up the requirements:

RequirementDirect routecgo route
IBM's Go fork for z/OSrequiredrequired
Access to a z/OS systemrequiredrequired
A C compiler on z/OSnot neededrequired
Language Environmentonly the Malloc31 touchpointfull dependency
Parameter-list knowledgerequired — and obtainednot needed

The cgo route is a superset of the direct route's dependencies. If the two remaining risks materialise — no z/OS access, or no Go fork — the cgo version cannot be built or run either. It insures against nothing that can actually happen, while costing the thesis its central claim.

The one thing it did insure against — "we cannot work out the parameter list" — is exactly the risk that has now been retired.

This is also a good thing to say out loud to Jürgen, because it shows you understood your own hedge well enough to see when it stopped being one. That reads better than either keeping it out of caution or dropping it out of confidence.

6 · So the question is

Given that the cgo path cannot survive the failures it was meant to insure against, and that Phase 3c already plans a latency comparison against __console2() anyway — do you want to close roadmap question 1, and if so, does cgo disappear entirely or survive as a measurement baseline?
